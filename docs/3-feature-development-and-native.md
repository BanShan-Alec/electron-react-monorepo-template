# 阶段三：业务功能与 Native 原生模块

本文档阐述模板在业务功能扩展、多语言国际化体系与 C++ 原生模块集成上的架构方案与设计理由。

## 1. 解决什么工程痛点

随着桌面应用功能不断扩展，代码库容易出现以下工程失控现象：
- **目录扁平膨胀**：组件、Hook 和全局状态散落在不同顶级目录，删除一个功能时无法安全清理孤立代码。
- **国际化维护成本高昂**：多语言 JSON 手工维护繁琐，改动代码后经常忘记补充对应的语言词条，导致生产环境展示空白或键名泄露。
- **C++ 原生模块打包即崩溃**：引入 `usb`、`serialport` 等依赖后，本地开发正常，但打包为 asar 生产包后，由于动态链接库 (`.node`) 无法在归档内直接加载 (`dlopen`)，导致应用在用户电脑上闪退。

## 2. 本模板做了什么

本模板为业务演进提供了高内聚结构与工业级原生依赖支持：

### 领域内聚的 Feature 架构
- 渲染层采用特性驱动架构（Feature-Driven Architecture）。
- 每一个独立业务功能（如设备管理、仪表盘、更新器）拥有专属子目录，内聚独立的组件 (`components`)、逻辑封装 (`hooks`) 与状态，提供清晰的生命周期边界。

### 编译期 AST 宏国际化提取 (Lingui v5)
- 源码中直接书写母语代码，使用编译期 `t` 宏包裹词条。
- 借助 Babel/Lingui 静态分析工具自动扫描源码并同步生成 PO 文件，不再依赖人工手写映射表。
- 构建期将 PO 词条编译为轻量化 JavaScript 二进制，体积小且查询性能极高。

### pnpm 隔离架构下的 Native Addon 自动提升与解包
- 在保持 `node-linker=isolated` 高隔离依赖树的前提下，通过 `.npmrc` 中的 `public-hoist-pattern` 规则自动提升特定原生二进制。
- 打包流水线自动配置 `asarUnpack: ['**/*.node']`，构建时将 `.node` 及其依赖自动放置在 `app.asar.unpacked/` 外置目录中。
- 主进程通过 `__dirname` 相对路径解析，在开发期与生产期保持一致的寻址逻辑。

## 3. 为什么这样设计

- **为什么采用 Feature 结构而不是横向分层目录？**  
  横向分层（所有组件放在 `components`、所有 Hook 放在 `hooks`）在大型项目中会导致代码边界模糊，开发时需要在不同深层目录间频繁跳跃。Feature 结构使得功能模块具有高内聚性，便于重构、独立测试和快速删除。

- **为什么坚持使用 Lingui 宏而不是传统的 i18next 键值映射？**  
  传统的 `t('home.dashboard.welcome_title')` 缺乏类型安全且与上下文脱节，代码可读性差。源码直接写母语文本并通过 AST 宏提取，不仅具备天然的上下文可读性，还能通过静态分析在编译期发现未翻译词条。

- **为什么采用公有提升与精准 asarUnpack 方案，而不是粗暴禁用 asar 或干掉依赖隔离？**  
  禁用 asar 会导致成千上万的小文件散落在安装目录，极大地拖慢 Windows 系统的启动与 I/O 速度，并直接暴露源代码；而关闭 pnpm 隔离会导致整个项目退化为充满幽灵依赖的扁平目录。针对原生模块按需提升与精准解包，既保留了 100% 的依赖安全性，又完美解决了原生库加载问题。
